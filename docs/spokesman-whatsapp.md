# Spokesman — WhatsApp channel (provisioning runbook)

The **Spokesman** is the stakeholder communication service (ADR-0006). This
runbook provisions its **WhatsApp** channel end-to-end: a containerized
FastAPI service that

- receives inbound messages via a Meta **WhatsApp Business Cloud API** webhook
  (signature-verified),
- pushes 🚨 **alarms** immediately and batches 🛑 **approve** / 📣 **inform**
  items into a periodic **digest**,
- routes inbound messages into the git `state/` tree and answers `status`
  (ADR-0007).

All secrets/config come from the environment; nothing sensitive is committed
(ADR-0011). The service runs with **no live credentials** in dry-run mode
(`SPOKESMAN_DRY_RUN=1`) — outbound sends are logged instead of called out.

---

## 0. Prerequisites

- M0 infra spine bootstrapped (see [`PREREQS.md`](../PREREQS.md)) — not strictly
  required to start the Spokesman, but that's the normal host state.
- A **Meta** account and a phone number you can use as the WhatsApp Business
  sender (the Cloud API provides a free test number to start).
- A way to expose the webhook publicly (a tunnel — cloudflared below).

## 1. Create the Meta app + WhatsApp product

1. Go to <https://developers.facebook.com/> → **My Apps** → **Create App** →
   type **Business**.
2. In the app dashboard, **Add product → WhatsApp → Set up**. This creates a
   test **Business Account** and a test **phone number**.
3. Note the **Phone number ID** and **WhatsApp Business Account ID** from
   *WhatsApp → API Setup*. These are **not secret** but are config.

## 2. Collect the token, phone-id, and app secret

- **Access token:** the API Setup page shows a temporary token. For a durable
  deployment create a **System User** with a **permanent token** scoped to
  `whatsapp_business_messaging` + `whatsapp_business_management`
  (*Business Settings → Users → System Users*). This is a **secret**.
- **App secret:** *App Settings → Basic → App Secret*. Used to verify the
  `X-Hub-Signature-256` on every inbound webhook. **Secret.**
- **Phone number ID:** from *WhatsApp → API Setup* (config, not secret).

## 3. Choose a verify token

Pick any high-entropy string (e.g. `openssl rand -hex 24`). You give the same
value to Meta and to the service; it's only used for the one-time subscription
handshake. Treat it as a **secret**.

## 4. Store everything via onboarding

Run the cold-start flow, which writes to a git-ignored `.env` (ADR-0011):

```bash
./scripts/onboarding.sh
```

It prompts for (under *Stakeholder WhatsApp*):

| Variable | Secret? | Where it came from |
| --- | --- | --- |
| `WHATSAPP_PHONE_NUMBER_ID` | no | API Setup |
| `WHATSAPP_BUSINESS_ACCOUNT_ID` | no | API Setup |
| `WHATSAPP_ACCESS_TOKEN` | **yes** | System user token |
| `WHATSAPP_APP_SECRET` | **yes** | App Settings → Basic |
| `WHATSAPP_VERIFY_TOKEN` | **yes** | you choose (step 3) |
| `STAKEHOLDER_WHATSAPP_NUMBER` | personal | your WhatsApp number, E.164 digits (e.g. `15551234567`) |
| `SPOKESMAN_API_TOKEN` | **yes** | auto-generated by onboarding; gates the control plane |

Non-secret Spokesman config (defaults are fine) lives in `.env.example`:
`SPOKESMAN_PORT` (8080), `SPOKESMAN_DRY_RUN` (0), `GRAPH_API_BASE`,
`GRAPH_API_VERSION`, `AI_STUDIO_STATE_DIR`.

## 5. Expose the webhook with a tunnel (cloudflared)

The Cloud API only calls **HTTPS** webhooks, so the local port must be public.

```bash
# One-off (quick tunnel; prints a https URL):
cloudflared tunnel --url http://localhost:8080

# Or a named tunnel using the token collected by onboarding:
#   CLOUDFLARED_TUNNEL_TOKEN in .env; run `cloudflared tunnel run`.
```

Note the public URL, e.g. `https://spokesman.example.com`. Your webhook URL is
`https://<public-host>/webhook`.

## 6. Start the service

```bash
docker compose --profile spokesman up -d spokesman
# health check:
curl -s http://localhost:${SPOKESMAN_PORT:-8080}/health
# -> {"status":"ok","dry_run":false,"pending_digest":0}
```

The `spokesman` service is behind a **compose profile**, so a plain
`docker compose up` (the M0 spine) is unaffected — it starts **only** with
`--profile spokesman`.

To smoke-test with no Meta credentials, set `SPOKESMAN_DRY_RUN=1` in `.env`
first; outbound messages are logged rather than sent.

## 7. Register the webhook + subscribe

1. In the Meta app: *WhatsApp → Configuration → Webhook → Edit*.
2. **Callback URL:** `https://<public-host>/webhook`
3. **Verify token:** the `WHATSAPP_VERIFY_TOKEN` from step 3/4. Meta issues a
   `GET /webhook?hub.mode=subscribe&hub.verify_token=…&hub.challenge=…`; the
   service echoes the challenge when the token matches.
4. Click **Verify and save**.
5. Under **Webhook fields**, **Subscribe** to `messages`.

## 8. Verify end-to-end

- Send a WhatsApp message to the business number → it appears (masked sender)
  in `state/inbox/whatsapp-inbound.jsonl` (git-ignored).
- Send `status` → you receive a summary of `state/status.md` back.
- Trigger an alarm (control plane needs the token):
  `curl -XPOST localhost:8080/notify -H "X-Spokesman-Token: $SPOKESMAN_API_TOKEN" -H 'content-type: application/json' -d '{"kind":"alarm","text":"test"}'`
  → arrives immediately.
- Queue + flush a digest:
  `curl -XPOST localhost:8080/notify -H "X-Spokesman-Token: $SPOKESMAN_API_TOKEN" -d '{"kind":"inform","text":"fyi"}' -H 'content-type: application/json'`
  then `curl -XPOST localhost:8080/digest/flush -H "X-Spokesman-Token: $SPOKESMAN_API_TOKEN"` → one batched message arrives.

## API surface

| Method | Path | Auth | Purpose |
| --- | --- | --- | --- |
| GET | `/health` | public | liveness + dry-run + pending digest count |
| GET | `/webhook` | public | Meta verification handshake |
| POST | `/webhook` | HMAC signature | inbound messages (HMAC-SHA256 verified) |
| POST | `/notify` | `X-Spokesman-Token` | `{"kind":"approve\|inform\|alarm","text":"…"}` → classify + route |
| POST | `/digest/flush` | `X-Spokesman-Token` | send the pending approve/inform digest |

`/notify` and `/digest/flush` are the **control plane** and require the
`X-Spokesman-Token` header (matched against `SPOKESMAN_API_TOKEN`). They **fail
closed**: if `SPOKESMAN_API_TOKEN` is unset, both return `401`.

`/digest/flush` is intended to be driven by the scheduler (e.g. daily) once the
supervisor/scheduler milestone lands; until then call it manually or by cron.

## Security notes

- **Signature verification is mandatory.** Every `POST /webhook` must carry a
  valid `X-Hub-Signature-256` = `sha256=HMAC_SHA256(raw_body, APP_SECRET)`;
  mismatches are rejected with `403`.
- **The control plane is authenticated.** `/notify` and `/digest/flush` sit on
  the same publicly-tunneled port as `/webhook`, so they require the
  `SPOKESMAN_API_TOKEN` shared secret — otherwise an internet caller could inject
  spoofed alarms/approvals to the stakeholder.
- **Defense in depth — restrict the tunnel.** Configure the cloudflared tunnel to
  forward only `/webhook` and `/health` publicly (e.g. per-path ingress rules);
  keep `/notify` and `/digest/flush` reachable only on the local network. The
  token gate is the primary control; the tunnel scoping is a second layer.
- **No personal info in git.** Inbound sender numbers are masked to the last 4
  digits and message bodies are truncated to 4000 chars before being written; the
  inbound log is git-ignored (ADR-0011). It is short-lived working state, not a
  durable record — safe to rotate/delete once messages are processed.
- **Secrets never reach an agent.** The service (a tool) reads creds from the
  environment and calls the Graph API on the studio's behalf.
